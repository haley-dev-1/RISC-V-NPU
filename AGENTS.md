## 1. Hard Rules (Non-Negotiable)

1. TinyQV source files MUST NOT be modified.
   - All files under the TinyQV source directory are treated as frozen IP.
   - TinyQV must be integrated strictly through wrappers, interfaces, MMIO, and DMA.
2. All other RTL, testbenches, scripts, and documentation MAY be modified or added as needed.
3. ALL code must be generated by an LLM.
   - No human-written Verilog, testbench, or scripts.
4. Every design step must be logged in a prompt log.
5. Focus ONLY on:
   - tinyQV connection to MMIO
   - Dual-Channel DMA
   - Working end-to-end testbenches
6. EXISTING TESTBENCHES MUST NOT BE MODIFIED if they already pass.
   - Passing tests are treated as golden reference behavior.
   - If a new change breaks an existing passing testbench, the design must be fixed, not the test.
   - New functionality must be validated using new testbenches only.

## 4. Head Start on Core NPU Modules (MANDATORY DESIGN GUIDANCE)

The agent MUST design the following modules with the listed minimum features and dependencies.  
TinyQV modules themselves are NOT to be edited — these modules wrap or feed TinyQV.

### 4.1 Module Breakdown

| Module Name        | Must-Have Features                                           | Depends On          |
|--------------------|---------------------------------------------------------------|---------------------|
| mac32              | 32-bit signed MAC, overflow handling, saturation support     | None                |
| systolic_array     | Wavefront propagation, local weight storage (4x4 or 8x8)     | mac32               |
| sram_buffer        | Dual-port access (DMA write, Array read)                     | Array size          |
| dual_dma           | Strided 2D access, burst support, SRC/DST channels           | System bus spec     |
| npu_fsm            | Idle -> Load -> Compute -> Store states                      | DMA & Array         |
| tinyQV_top         | Wrapper adapting DMA/FSM to TinyQV interface                 | FSM & DMA           |

Array size choice must be justified in the prompt log with area/performance tradeoffs.

## 5. Focus Area A: tinyQV MMIO Integration

### Purpose
Expose TinyQV control and DMA descriptors via MMIO so the CPU can:
- configure operations
- launch TinyQV
- monitor status
- receive interrupts

### MMIO Register Map (32-bit)

BASE + 0x00 CMD
[0] START
[1] ABORT
[2] IRQ_EN
[3:7] OPCODE
[8:15] QPARAM

BASE + 0x04 STATUS
[0] BUSY
[1] DONE
[2] ERROR
[3] DMA_BUSY

BASE + 0x08 SRC_DESC_PTR
BASE + 0x0C DST_DESC_PTR
BASE + 0x10 CONTROL
BASE + 0x14 PERF_CNT_LO
BASE + 0x18 PERF_CNT_HI
BASE + 0x1C WATCHDOG


TinyQV must be controlled ONLY through this interface and wrapper logic.

---

## 6. Focus Area B: Dual-Channel DMA

### Required DMA Features

- Independent SRC (read) and DST (write) channels
- Descriptor-driven operation
- Strided 2D addressing
- Burst support
- Abort and error handling
- Bounds checking

### Required DMA Tests (dma_unit_tb.v)

1. Single descriptor copy
2. Multi-descriptor chain
3. Abort mid-transfer
4. Backpressure / stall injection
5. Invalid descriptor detection

All tests must self-check and print PASS or FAIL.

Existing DMA-related testbenches (if any) must remain unchanged if already passing.

---

## 7. Focus Area C: End-to-End Testbench

### e2e_npu_tb.v Must Demonstrate

1. CPU writes MMIO registers
2. Descriptor lists written to memory
3. Dual DMA transfers data
4. Data delivered to TinyQV via wrapper
5. TinyQV computation executes
6. DMA writes results back
7. CPU detects DONE or IRQ
8. Output memory matches software reference

The end-to-end testbench must coexist with all existing testbenches without modification.
